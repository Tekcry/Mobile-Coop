# S28 - guards route round locked doors (Marlow A7 `A7-cage-w` stall)

Branch `feature/guard-ai-s28` off master 79a527aa. Builder: Opus. Prototype stage (no refinement).

## Cause
- `src/ai/doorGate.ts:10-16` and `docs/systems/ai.md` (S20, A116): the nav grid kept every doorway walkable ("no closure
  per door"); only the walker's gate knew about leaves.
- `src/ai/enemyManager.ts:548-556` (`doorStep`): a shut leaf in his step is opened only when `!d.anchor.locked`; a locked
  one returns false every step, so he stands at the leaf.
- `src/ai/navGrid.ts:776-831` (`addClosure` / `setClosed`): the only runtime closures were Sector Ops' (keypad, bolt,
  lockdown, pair gate: `src/game/sectorStage.ts:78`, `src/game/sectorTeamDoors.ts`). Marlow's course gates
  (`src/game/modes/courseMode.ts:1032-1046` `applyLocks` -> `Doors.setLocked`) and every map door authored
  `locked: true` (A7's `A7-cage-w` / `A7-cage-e`, `src/world/maps/ctcourseSets/a7DataHall.ts:324-325`) changed only
  `anchor.locked` (`src/world/doors.ts:200` before this slice), which A*, `lineClear` and the flow field never read.
- So `Enemy.goTo` (`src/ai/enemy.ts:2128`) planned through the locked doorway (or walked the straight line, `lineClear`
  true) and the gate held him at the leaf until his route or state moved on (~15 s). The S20 walk check already named the
  fix (`docs/guard-ai/slices/WALK-CHECK.md:97`: "per-door nav closure while locked and shut").
- Key / access: none exists. `keyholder` (`src/ai/sectorTags.ts:40`, sector data) is a fixed-post role class, not door
  access, and the gate refuses a locked door to every guard. So every guard treats a locked shut door as a wall.

## Built
1. `src/ai/lockedDoors.ts` (new, pure): `LockedDoorNav` adds one nav closure per door (the Sector Ops door size:
   `STAGE_NAV_ACROSS` 0.35 deep, width + `STAGE_NAV_ALONG` 0.5 long, at the hinge height), and `sync()` holds it shut
   while `lockedShut(d)` (`anchor.locked && target === 0`; a locked door standing open stays walkable). Typed arrays,
   allocation-free after the constructor. Overlaps with Sector Ops' closures are counted per cell by `NavGrid.setClosed`.
2. `src/ai/enemyManager.ts` (`update`, next to the S20 gate build): builds `lockedDoors` on the first update with doors,
   calls `sync()` every update, and sets `Doors.onLocked` so a lock set between two updates (a script, the far side's
   Unbolt under `loop.manual`) reaches the grid at once.
3. `src/world/doors.ts`: `setLocked` returns early when nothing changes and calls the new `onLocked` hook.
4. Re-path: no new path code. `setClosed` bumps `NavGrid.version`, which already replans the manager's flow field and each
   held `goTo` route once (`routeVer`). `src/ai/enemy.ts` `goTo`: new `routeMiss` - a goal with no path is retried once a
   `routeT` (1 s), at a new goal (moved > 1.5 m) or at a grid change, not every frame (before: an empty route replanned
   every frame; a goal behind a locked door would have run a 3000-cell A* at 60 Hz). Unreachable goals fall back as
   before: a patrol point is walked at straight (the gate stops him short of the leaf), a search point is skipped
   (`enemy.ts` ~1469 / ~2300).
5. `scripts/e2e-course.mjs` (Fallow nav read, ~497): it asserted paths A5 -> S6 and B5 -> A5 with the comment "Nav does
   not model doors (closed or locked)". That read is the level's own connectivity; it now unlocks the locked doors for
   the query and locks them back inside the same `evaluate` (no frame between: the course state is untouched).

Not touched: `src/net`, the save shape, the door gate itself (still the fallback for a stale route or a straight walk).
