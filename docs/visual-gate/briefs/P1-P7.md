## How a builder reads the results
```bash
cd /c/NightShift/Mobile-Coop-visual-gate && git fetch -q origin shots/visual-gate-proofs shots/visual-gate-vg7
T=$(mktemp -d)   # outside the repo; never write results into the worktree
git archive origin/shots/visual-gate-proofs <tag> [<tag> ...] | tar -xf - -C "$T"     # -> $T/<tag>/<folder>/result.json, png/<key>.png
node scripts/visual-gate/noise.mjs proof --fn <Fn> --bad "$T/<bad tag>/<folder>/result.json" --fixed "$T/<fixed tag>/<folder>/result.json" --bad-label <bad tag> --fixed-label <fixed tag>
```
- `result.json` is the VG5 shape (RunRecord + `summary`, `warnings`, `runErrors`, `notRun`, `renderers`); each shot
  has `metrics` (or `error`) and `skips` (regions dropped: `behind`, `small` under 1500 px, `blotch-small`).
- PNGs: `png/<key>.png` (views and rig states, key `<id>@<preset>` / `<id>-on@<preset>`), `png/card-<view>-<k>.png`
  (960 x 540). Open them with the Read tool to eyeball each target.
- A missing `result.json` (gate crash) or a missing folder: write NOT MEASURED with the step it came from; the lead
  gets the step log from Test Runner. Never invent or carry numbers from another build.
- The noise: `scripts/visual-gate/tolerances.mjs` `SPREAD` (VG7, master, 3 runs) gives `sd` per key and metric;
  `noise.mjs proof` reads it and `TOLERANCES` itself.

## What "red on bad, green on fixed" means here (A30)
Per table row (one key x one metric, from `noise.mjs proof`):
- **SEPARATES**: the bad value sits on the bad side (`dir` ok) and |bad - fixed| >= 4 sd (`sep >= 4`). VG8 can then
  set a rule at about `mid` (PLAN :71) that is red on bad and green on fixed with 4-sigma room.
- **WEAK**: right direction, `sep` under 4. **WRONG WAY**: the bad build sits on the fixed side.
  **NOT MEASURED**: a null value; give the `note` (error, region skipped small / behind, not in run).
- `drift` yes: the baseline compare would flag that address if a release went from the fixed look to the bad one
  (with VG7's tolerances), so the train catches the regression even before VG8's rule.
- Rig rows (`leak.*`) have their rule already: `rule bad` red and `rule fixed` green is the proof itself.
Per Fn the verdict is **PROVEN** (the Fn's own criterion below holds and the PNGs show the fault on bad and not on
fixed), **PARTIAL** (some target rows separate, the rest do not; say which and why), or **NOT PROVEN**. A NOT PROVEN or
PARTIAL is a finding for VG8 and the lead (metric wrong for the target, region badly placed, view moved), never a
reason to change code here.
